CLI Evidence Guard (2026-07-04)
-------------------------------

LongMemEval eval/full500/summary/retry entrypoints reject duplicate boolean
mode flags and duplicate scalar source/output/run/budget selectors before report
generation or batch planning. Covered booleans include `--all-cases`,
`--continue-on-execution-failure`, `--resume-existing-shards`,
`--allow-duplicate-case-coverage`, `--dry-run`, and
`--resume-existing-batches`. Covered scalar selectors include `--benchmark-root`,
`--mode`, `--limit`, `--max-concurrency`, `--offset`, `--output-dir`,
`--run-id`, `--case-concurrency`, `--shard-concurrency`, `--shard-size`,
`--shards`, `--expected-total-cases`, `--batch-concurrency`,
`--batch-delay-ms`, `--chunk-size`, `--max-batches`, `--merged-run-id`, and
`--retry-run-id`; repeated multi-value selectors such as `--profile`,
`--case-id`, `--question-type`, `--shard-run-id`, and `--source-run-id` remain
repeatable. This protects accepted and public-claim source evidence from
repeated-switch ambiguity. Base eval, recall-diagnostic, full500 runner, and
full500 summary also require output `--run-id` values to be a single path
segment before deriving report, shard, or merged-report directories. This does
not change the 0.720 judge-free public claim or the older with-judge internal
checkpoint.

Base eval/readiness benchmark-root resolution now rejects empty or
whitespace-padded `GOODMEMORY_LONGMEMEVAL_ROOT` fallback values before
source-root resolution. Explicit `--benchmark-root` values still take
precedence, and smoke-mode fixture defaults still bypass the external-root env
fallback. This protects accepted LongMemEval smoke/full and recall evidence
from malformed env-derived source roots without changing the 0.720 judge-free
public claim or the older with-judge internal checkpoint. Unit coverage lives in
`tests/unit/run-phase-62.script.test.ts`.

`gate:phase-62` also rejects duplicate scalar gate output selectors
(`--output-dir`, `--run-id`) before running LongMemEval smoke gate checks or
writing gate artifacts, and requires `--run-id` to be a single path segment so
gate artifacts stay under the intended quality-gates directory. This protects
accepted LongMemEval gate evidence from repeated-selector ambiguity and
gate-directory traversal without changing the 0.720 judge-free public claim
or the older with-judge internal checkpoint.

`eval:phase-62-deterministic-subset` also rejects duplicate scalar
report/output/profile selectors (`--report-path`, `--run-id`, `--output-dir`,
`--claim-profile`, `--baseline-profile`) before resolving the source report,
and requires `--run-id` to be a single path segment so implicit source-report
paths stay under the intended Phase 62 output directory. This protects the
judge-free LongMemEval public-claim helper from repeated-selector ambiguity and
source-report traversal without changing the 0.720 claim.


Driver
------

The selected external benchmark order is:

1. LongMemEval
2. BEAM
3. MemoryAgentBench
4. LoCoMo

LongMemEval goes first because it directly tests long-term chat memory across
information extraction, multi-session reasoning, knowledge updates, temporal
reasoning, and abstention.


Accepted Scope
--------------

- LongMemEval smoke adapter with synthetic shape-compatible fixtures.
- External `--benchmark-root` support for full LongMemEval data without
  vendoring upstream benchmark files.
- Baseline profiles:
  - `baseline-no-memory`
  - `baseline-full-context`
  - `goodmemory-rules-only`
  - `goodmemory-hybrid`
- Report fields for answer correctness, evidence-session recall, missed recall,
  wrong recall, abstention correctness, and question-type breakdown.
- LongMemEval miss-case taxonomy and targeted GoodMemory repairs after the
  first full run.


Out Of Scope
------------

- final public benchmark report
- BEAM, MemoryAgentBench, or LoCoMo adapters
- README-level LongMemEval claim from the Phase 62 with-judge/hybrid checkpoint
  itself; the later P67-B public claim is a separate judge-free deterministic
  subset with its own declaration and gate.
- vendoring full LongMemEval data
- benchmark-specific runtime hacks
- public API or public config widening

Commands
--------

```text
bun run eval:phase-62
bun run gate:phase-62
bun run eval:phase-62 -- --mode full --benchmark-root <LongMemEval data root> --max-concurrency 1
bun run eval:phase-62-full500 -- --benchmark-root <LongMemEval data root> --run-id <full-500-run-id> --resume-existing-shards
bun run eval:phase-62-full500-summary -- --run-id <full-500-run-id>
bun run eval:phase-62-full500-retry-failures -- --benchmark-root <LongMemEval data root> --source-run-id <merged-or-shard-run-id> --retry-run-id <retry-run-id> --merged-run-id <merged-run-id> --chunk-size 10 --batch-concurrency 1 --case-concurrency 1 --resume-existing-batches
bun run eval:phase-62 -- --mode full --benchmark-root <LongMemEval data root> --question-type multi-session --limit 3 --max-concurrency 1
bun run eval:phase-62-recall-diagnostic -- --mode full --benchmark-root <LongMemEval data root> --profile goodmemory-rules-only --max-concurrency 1
```

If provider failure stops a retry run normally, use the emitted merged run as
the next `--source-run-id`; it preserves successful batches and leaves only
unresolved `executionError` rows retryable. If a retry run is manually
interrupted before it can emit a merged report, rerun the same `--retry-run-id`
with `--resume-existing-batches`. The runner discovers completed
`*-batch-NNN` reports under the output directory, merges their successes, and
continues numbering from the next batch instead of requiring a manual source
